## 1. 專案背景

使用者是建築/工程技術服務建議書的**業務投標手**，工作內容是在「備標期」內把所有投標文件準備齊全並送出。
這個工具的目的：**新增一個案件後，自動依照公司內部真實的備標作業流程，產生一份完整的待辦清單＋時程表**，
並提供清單檢視與行事曆檢視兩種操作介面，讓使用者能：

- 快速掌握目前案件的整體進度
- 知道每一項任務的到期日、負責人
- 用行事曆直覺地調整/新增/拖曳時程
- 對「重點大事記」（9 個關鍵里程碑）保持隨時可見的追蹤

## 2. 資料結構（Data Model）

### 2.1 最外層 STATE
```js
STATE = {
  cases: { [caseId]: Case },
  lastActiveId: string | null
}
```
儲存在 `window.storage` 的 key `bid-cases`（`shared:false`，僅該使用者可見），存的是 `JSON.stringify(STATE)`。

### 2.2 Case 物件
```js
Case = {
  name: string,                // 案件名稱
  workStart: 'YYYY-MM-DD',     // 開始作業期程（內部真正開始備標作業的日子，可能早於招標公告）
  start: 'YYYY-MM-DD',         // 招標公告時間（過去版本叫「領標日」，是排程規則的主要錨點，見第4節）
  deadline: 'YYYY-MM-DDTHH:MM',// 投標截止（日期＋時間，datetime-local 格式）
  bidLead: string,             // 主投標手姓名（負責人下拉選單的預設選項來源）
  meetingWeekday: 0-6,         // 例行會議固定星期（0=週日...6=週六）
  contractAmount: number,      // 契約金額（新台幣元）→ 決定標前會場次（≥80億=3場，否則1場）
  siteArea: number,            // 基地面積（m²）
  floorArea: number,           // 總樓地板面積（m²）
  floorCount: string,          // 預計設計樓層（文字，如「地上20層/地下4層」）
  weekNotes: { [weekStartISO]: string }, // 行事曆檢視「本週目標/備注」欄位的自由文字
  team: {
    architect: string[],       // 建築師姓名清單（自由新增/刪除）
    mep: string[],             // 機電團隊姓名清單（自由新增/刪除）
    consultants: [{            // 專業顧問（固定13個角色 + 可自訂新增）
      role: string,            // 專業顧問角色名稱
      company: string,         // 顧問工程公司名稱
      contact: string,         // 負責人姓名
      affiliation: string,     // 所屬（如 MAYU／建國）
      custom: boolean          // true=使用者自訂新增的角色（可刪除）；false=系統13個預設角色（不可刪除，只能編輯內容）
    }]
  },
  tasks: [Task]
}
```

### 2.3 Task 物件
```js
Task = {
  id: string,
  cat: string,        // 分類，見第3節（A~F 其中一個分類字串）
  label: string,       // 任務名稱
  owner: string,       // 負責人/單位（下拉選單）
  due: 'YYYY-MM-DD',    // 到期日
  done: boolean,
  milestone: string | null  // 若為9個重點大事記之一，填對應 key（見第5節），否則 null
}
```

### 2.4 專業顧問預設13個角色（`CONSULTANT_DEFAULTS`）
```
結構技師、機電技師、空調技師、景觀顧問、交通技師、
水保/出流(水利技師)、大地技師、智慧建築顧問(設計階段)、
綠建築/能效顧問(設計階段)、低碳顧問(設計階段)、
微振顧問、施工監測技師、生態檢核
```
新增案件時**不會**自動帶入這13項（目前版本考量表單越簡越好），但團隊面板顯示時
（`normalizeTeam`）會自動補齊缺少的預設角色，確保永遠有這13列可填。

## 4. 自動排程規則引擎（`generateTasks(c)`）

**核心觀念**：`c.start`（招標公告時間）是大多數規則的計算錨點；`c.deadline`（投標截止）是另一個錨點；
`c.workStart`（開始作業期程）只用來決定「備標天數」的顯示與行事曆的顯示範圍，**不會**改變任務的排程日期計算。

輔助函式：
- `addDays(date, n)`：日期加減天數
- `snapToBizDay(date)`：如果算出來的日期落在週六，往前推1天；落在週日，往前推2天（避開假日）
- `generateRecurringMeetings(start, deadlineDate, weekday)`：從 `start+3天` 開始找下一個符合 `weekday` 的日子，
  之後每週一次，直到 `deadline-7天` 為止（最多20場）

### 4.1 會議安排
| 任務 | 時間規則 |
|---|---|
| 例行會議 #01~N | 每週固定星期一次，從開案後約1週開始，排到截止前1週為止 |
| 統包啟動會議 | **招標公告前一週**（`start - 7天`，需與使用者確認方向是否正確） |
| 內部（董事會）期初成果報告 | `start + 10天` |
| 吳董設計會議（設計定稿） ★大事記② | 招標公告後 **3~4週**（目前取中間值 `start + 24天`），全案只會發生一次 |
| 標前會 ★大事記⑤ | 契約金額 **≥80億→3場**（截止前7/5/3天），**<80億→1場**（截止前4天），都在投標前7天內 |
| 備標團隊公證 ★大事記④ | **投標前一週**（`deadline - 7天`），前提是標前協議書已簽署完成（僅文字註記提醒，非真正的邏輯依賴） |

### 4.2 公司內部流程
| 任務 | 時間規則 |
|---|---|
| 標前協議書／共同投標協議書確認 | 投標截止前一週完成 |
| 營繕工程備標申請（簽呈送出） | 招標公告後3天內 |
| 會辦流程單（契約、投標須知） | 招標公告後3天內 |
| 會辦流程單（備標團隊標前協議書，不含金額） | 招標公告後2~3週（取中間值18天） |
| 工程事業簽呈（標前協議書含費用、共同投標協議書含費用） ★大事記③ | 標前會議前完成（取最早一場標前會前3天）——**此規則使用者尚未給明確天數，是暫定值，需再確認** |

### 4.3 投標文件蒐集、確認
| 任務 | 時間規則 |
|---|---|
| 招標公告 ★大事記① | = `c.start`（就是這個日期本身） |
| 投標前估算數量（估算部，2週作業） | 開始日 = 標前會前1週再往前推2週 |
| 估算部完成估算 | 標前會前1~1.5週 |
| 建築師提供平立面／剖面／門窗表／外觀材質 | 估算部開始作業前1天 |
| 投標成本定稿 | 標前會前5天 |
| 內部成本簽核 / 內部標前會議 | 標前會前1天 |
| 內部核決 | 標前會後1天 |
| 確認設計顧問委託及顧問團隊 | 招標公告後一週內 |
| 投標資格文件彙整 | 投標截止前一週 |
| 押標金 | 截止前8天 |
| 投標資格實績公證＋統包廠商JV公證合作同意書（合併為一項） | 投標截止前一週內 |
| 送件投標 ★大事記⑧「投標時間」 | **投標截止前一天**（因為投標時間通常早上9點，實務上會提早一天送件），會自動避開週末 |
| 投標截止 ★大事記⑨ | = `c.deadline` 當天 |

### 4.4 服務建議書製作
| 任務 | 時間規則 |
|---|---|
| 服務建議書母片／分工表提供 | 招標公告後2週 |
| 服務建議書初稿繳交 | 母片提供後約1.5週、最接近的一場例行會議的**前一天** |
| 服務建議書校正＃1 | 上述那場例行會議**當天**（彙整用） |
| 服務建議書校正＃2 ★大事記⑥「最後校稿」 | 送印前2天 |
| 服務建議書送印 ★大事記⑦ | 投標截止前2天，遇到週末會自動往前推到最近的週五 |
| 服務建議書用印（含封標） | 送印前1天 |

### 4.5 評選作業（投標截止後才發生的項目，行事曆會延伸開放到截止後1個月）
| 任務 | 時間規則 |
|---|---|
| BIM模型動畫模擬工序 | 截止前10天 |
| 完成建築設計動畫（90秒） | 截止前5天 |
| 施工評選簡報初稿 | 截止前3天 |
| 施工評選簡報定稿 | 截止後1天 |
| 簡報模擬 | 截止後3天 |
| 施工評選簡報（業主端） | 截止後5天 |
| 決選廠商 | 截止後20天 |

### 4.6 其他事項（業主流程、設計進度等，沿用經驗比例，非硬性規則）
- 公開招標、疑義澄清、投標／開標作業（業主流程）
- 初步設計規劃、設計圖說V2、投標前設計圖說定稿、BIM綠能分析、建材設備選用表、建築模型1/100、工程進度／工序定稿

> 這些是早期沒有明確規則的項目，用「距截止日的比例（fraction）」反推日期，之後如果使用者提供更精確的規則，
> 應該把這些也改成明確的天數規則。

## 5. 重點大事記追蹤（9項，`MILESTONE_ORDER`）

```js
[
  {key:'collect',       label:'① 招標公告'},
  {key:'wu',             label:'② 吳董會議'},
  {key:'eng_signoff',   label:'③ 工程事業簽呈'},
  {key:'notarize',       label:'④ 公證時程'},
  {key:'prebid',         label:'⑤ 標前會'},
  {key:'final_proof',   label:'⑥ 服務建議書最後校稿'},
  {key:'print',          label:'⑦ 服務建議書送印'},
  {key:'submit_action', label:'⑧ 投標時間（實際送件）'},
  {key:'deadline',       label:'⑨ 投標截止時間'}
]
```

**呈現方式（重要的 UX 決策）**：
- **沒有**獨立的大事記打勾清單（曾經做過又拿掉了）。
- 大事記的完成狀態**完全來自清單檢視的打勾**（`task.done`），因為每個大事記本質上就是某個 `task.milestone` 對應的任務。
- 「整體進度」區塊的進度條上方，會疊加顯示 🚩 旗標圖示，依照該任務到期日在時間軸上的相對位置浮動，顏色/動畫依狀態變化：
  - 已完成：旗標變灰、半透明
  - 未完成但快到期：正常顯示
  - **已逾期未完成**：旗標會有跳動放大＋陰影的動畫（CSS `@keyframes msBlink`）

> **Next.js 版更新**：旗標已改為動態圓點（依「已完成 / 快到期 / 已逾期 / 正常」四態變色＋脈動動畫），
> 詳見 [`docs/決策.md`](./決策.md)。

## 6. 主要功能與 UI 規格

### 6.1 案件資訊面板（可收合，`<details>`）
- 分「檢視模式」與「編輯模式」：
  - 檢視模式：唯讀文字顯示所有欄位（開始作業期程、招標公告時間、投標截止、備標天數、主投標手、
    例行會議星期、契約金額、基地面積、總樓地板面積、預計設計樓層）
  - 編輯模式：所有欄位變成可編輯的 input/select
- **只有編輯模式**才會顯示：
  - 「上傳招標文件（PDF）自動判讀」功能（見6.5）
  - 「重新依目前設定產生排程（覆蓋所有任務）」按鈕
  - 這兩個放在面板**右下角**
- 收合開關狀態（開/關）會被記住，**不會**因為切換清單/行事曆檢視、或做其他操作而自動被打開——
  這是使用者明確要求的行為，因為每次都要滑到最下面編輯很困擾。
- 新增案件當下，此面板會自動展開＋進入編輯模式，方便直接補齊資訊；除此之外的任何時候（切換案件、
  從專案管理開啟、任何 re-render）都維持使用者手動設定的開關狀態。

### 6.2 備標團隊成員面板（可收合，`<details>`）
- 一樣分「檢視模式」與「編輯模式」
- **檢視模式**：用「小型組織圖卡片」並排呈現（`flex-wrap` 卡片網格），不是長條列表。每張卡片：
  上面小字是角色（建築師/機電團隊/該顧問角色名稱），下面是對應的姓名。
- **編輯模式**：
  - 建築師、機電團隊：直向列表，一行一個姓名輸入框＋刪除按鈕，可自由新增/刪除
  - 專業顧問：固定表格（專業顧問／顧問工程／負責人／所屬 四欄），13個預設角色**不可刪除**（只能編輯內容），
    使用者額外新增的自訂角色才能刪除
- 開合狀態記憶邏輯同案件資訊面板。

> **Next.js 版更新**：團隊面板已改為「建築師團隊／建國工程團隊」兩個並排框框＋可拖曳分類顧問，
> 檢視模式改為樹狀組織圖，詳見 [`docs/決策.md`](./決策.md)。

### 6.3 清單檢視
- 依 6 大分類分組顯示，每組內任務**依到期日自動排序**（每次資料變動都會重新排序）
- 每個任務列：打勾框、任務名稱（可編輯）、**負責人下拉選單**（見下）、到期日（星期＋日期選擇器）、刪除按鈕
- 負責人下拉選單選項來源（`getOwnerOptions(c)`）：主投標手 + 建築師姓名 + 機電團隊姓名 + 顧問負責人姓名 +
  固定選項（業主／估算部／模型資訊部／建築師／機電團隊），並去重；若任務原本的 owner 不在清單裡也會保留顯示
- 新增的自動排程任務，若沒有指定特定負責人，**預設帶入主投標手姓名**
- 每個分類標題有色塊＋字母代號＋圖示

### 6.4 行事曆檢視（**系統主要操作介面，預設開啟**）
- Sun~Sat 週表格式，依月份分段（月份標題列 + 星期標題列），最後一欄是「本週目標/備注」自由文字欄
- 顯示範圍：`min(workStart, start)` 到 `deadline + 30天`（投標截止後保留1個月給評選作業用）
- 範圍外的日期（超出 workStart~deadline 的「其他事項」等）會有較淡的網底，但**不鎖定**——
  拖曳事件到範圍外的格子一樣可以放
- 每個日期格：
  - 右上角一個「＋」按鈕 → 點擊跳出「新增事件」小視窗（選分類 + 打事件名稱 + 確認），
    新增後自動歸到那一天、owner 預設主投標手
  - 事件卡片可以**拖曳**到別的日期格，放開後直接改期，並自動與清單檢視同步（因為是同一份資料）
  - 大事記項目的卡片有 ★ 標記與金色外框特別呈現
  - **今天**的日期格：綠色外框 + 📍圖示 + 「今天」文字
  - 有「已逾期」或「2天內到期」且未完成任務的日期格：紅色邊框**脈動動畫**提醒（`cal-day-alert` class）

### 6.5 招標文件自動判讀（PDF）
- **重要限制**：使用者原本希望用 `microsoft/markitdown`（Python 套件），但這個工具是純瀏覽器端 HTML/JS，
  沒有 Python 執行環境，無法安裝或呼叫 Python 套件。
- **目前的替代方案**：用 `pdf.js`（透過 cdnjs 載入的 JS 函式庫）在瀏覽器端直接把 PDF 轉成純文字，
  只把「抽出來的文字」（而不是整份 PDF 檔案）送給 Claude API 判讀，藉此大幅降低 token 用量。
- 呼叫 Claude API 的方式：`fetch('https://api.anthropic.com/v1/messages', ...)`，
  `model: 'claude-sonnet-4-6'`，`content` 只有一個 `type:'text'` block（PDF抽出的文字＋提示詞），
  要求回傳單純 JSON：`{contract_amount, site_area, total_floor_area, floor_count, submission_deadline}`
- 若 PDF 是純掃描圖檔（抽不出文字，`text.trim().length < 50`），會丟出明確錯誤訊息提示使用者改手動輸入。
- 判讀完成後用**畫面內自訂彈窗**（見6.7）顯示結果摘要，使用者確認才會套用到案件資訊。

> **Next.js 版狀態**：此功能尚未實作（見 [`docs/決策.md`](./決策.md) 的說明——原做法需要在前端硬編碼 Claude API
> Key，不安全，需等後端代理層完成後再補上）。

### 6.6 系統警示功能
- **整體進度上方的警示橫幅**（`buildAlertBanner`）：只要有「已逾期」或「2天內到期」且未完成的任務，
  就會顯示一個會發光脈動的警示橫幅（逾期時變紅色），列出最多6個項目
- **每個警示項目都是可點擊的按鈕**：點擊後會自動切換到清單檢視、捲動到該任務所在列，
  並閃一下金色高亮（`flash-highlight` class，2.2秒後消失）
- 行事曆上對應日期格也會有紅色脈動邊框（見6.4）

### 6.7 自訂確認/提示彈窗（`customConfirm` / `customAlert`）
- **重要**：不要用瀏覽器原生的 `confirm()` / `alert()`——這個工具跑在受限制的沙盒環境裡，
  原生對話框常常會被擋掉或無法正常回應，導致按鈕看起來「按了沒反應」。
- 一律用畫面內自己畫的 modal（`.modal-overlay` + `.modal-box`），回傳 Promise，
  在需要確認的地方用 `await customConfirm(...)` / `await customAlert(...)`。

### 6.8 專案管理介面
- 側邊欄不再放「刪除案件」按鈕（原本放在案件內部容易誤觸/找不到）
- 左下角固定一個「🗂 專案管理」懸浮按鈕（`position:fixed`），點開後是一個表格：
  案件名稱／開始作業期程／投標截止／剩餘天數／進度／開啟／刪除
- 刪除案件一樣要用 `customConfirm` 二次確認

### 6.9 已移除的功能
- **PPT 匯出功能已完全移除**（曾經用 `PptxGenJS` 做過，會讓系統不穩定當機，使用者要求拔除）。
  如果之後要重做，建議：
  - 換一個更穩定的 pptx 生成方式（例如透過真正的後端服務，或用 Claude Code 的 pptx skill 產生，而不是在瀏覽器端跑一個大型函式庫）
  - 內容需求：封面、案件資訊、備標團隊、整體進度＋大事記狀態、行事曆（依月份分頁），
    且行事曆要標註「輸出當天」的日期格

## 8. 已知問題與踩過的坑

1. **`render()` 函式曾被誤刪**：在移除 PPT 功能時，用「行號範圍刪除」的方式刪程式碼，
   結果連 `function render(){ renderTabs(); renderMain(); }` 都一起刪掉了，
   導致整個系統只要有任何互動就會 `Uncaught ReferenceError: render is not defined` 而「當機」。
   **教訓：刪除程式碼區塊時務必先精準定位起訖字串，而不是用暫存的行號（行號會因先前的編輯而位移）。**
2. **瀏覽器原生 `confirm()`/`alert()` 在這個沙盒環境會被擋掉**，一律要換成自製的 modal（見6.7）。
3. **PptxGenJS 在瀏覽器端跑起來不穩定**，會讓整個 artifact 當機，已完全移除。
4. **`microsoft/markitdown` 是 Python 套件，無法在純前端環境使用**，已改用 `pdf.js`（JS）做文字抽取。
